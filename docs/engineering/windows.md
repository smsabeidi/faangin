# Windows engineering record

November 2, 2026 · Faangin 0.4.3 · Windows port implemented in the shared codebase; no Windows machine has run the app

This record describes what the Windows build is, which code decides each OS difference, and which claims are verified by tests on macOS or by CI versus which still need a physical Windows machine. Nothing below was observed on Windows hardware. Where a statement rests on Electron's documented behaviour, the `@platform` annotations in `node_modules/electron/electron.d.ts` (Electron 44.7.0) are the source.

## Status and support matrix

| Target | State |
| --- | --- |
| Windows 10 version 2004 (build 19041) and later, x64 | Packaged target. 2004 is the floor because `WDA_EXCLUDEFROMCAPTURE`, the display affinity behind the optional screen-capture exclusion, first shipped there |
| Windows 11, x64 | Packaged target; same binary as Windows 10 |
| Windows on ARM | Not packaged. `electron-builder.yml` lists only `arch: [x64]`; nothing in the platform layer is architecture-specific, but no arm64 installer is produced or tested |
| Windows 10 before 2004, Windows 8.1 and earlier | Not supported. Electron 44 requires Windows 10 or later; older Windows 10 builds degrade content protection to `WDA_MONITOR` (a black rectangle in captures) |
| Remote Desktop and virtual machines | Separate configurations. Loopback audio, display affinity and topmost ordering can behave differently in remote sessions; results from them are not extrapolated to a physical console |
| Linux | Not a packaged target. `src/main/platform/linux.ts` keeps the pre-port behaviour (unknown permission statuses treated as not required, `basic_text` safeStorage rejected, 22 px tray icon) so development builds keep working |

What exists in the tree: the `DesktopPlatform` contract and its three implementations, Windows shortcut rules, the ICO pipeline, NSIS installer configuration, a signed-release script, a CI workflow with a `windows-latest` job, and unit tests that exercise the win32 branches with explicit platform ids. What does not exist: any run of the app on Windows, a Windows-built installer, a signed installer, or acceptance of audio, overlay, shortcuts, tray or installer behaviour on a physical machine.

## Architecture of the port

Every operating-system difference in the main process is expressed once, in `src/main/platform/types.ts`, as the `DesktopPlatform` interface: a set of read-only facts (`id`, `displayName`, `settingsAppName`, `appPresence`, `recoveryMenuName`, `supportsHiddenAppIcon`, `quitsWhenAllWindowsClosed`, `screenPermissionRequired`, `screenAccessGatesSystemAudio`, `promptsForMicrophone`, `supportsWindowMaterial`, `credentialStoreName`, `appUserModelId`, `defaultDeviceName`) and a set of decisions (`permissionStatus`, `permissionSettingsUrl`, `systemAudioUnavailableMessage`, `microphoneAccess`, `pendingMicrophoneMessage`, `overlayWindowOptions`, `workspaceWindowOptions`, `windowBackground`, `applyWindowMaterial`, `applyOverlayLevel`, `subscribeAccessibilityChanges`, `trayIcon`, `credentialEncryptionAvailable`, `credentialUnavailableMessage`). The implementations are `darwin.ts`, `win32.ts` and `linux.ts`; `src/main/platform/index.ts` selects one from `process.platform` and exports it as `platform`.

`src/main/index.ts` imports `platform` and calls `platform.*`. It never branches on `process.platform` for behaviour; the string appears only as data in the permissions payload sent to the renderer and in the diagnostic export. The renderer receives `permissions.platform` and uses it for labels (`Menu bar` versus `Tray`, Command versus Control) and to hide the macOS-only **Hide Dock icon** toggle; `AccessSetupCoordinator` uses it to map Linux's unreadable statuses to `not-required`. Keeping the checks in one place means macOS behaviour is unchanged byte for byte by the port: `darwin.ts` carries today's accessory Dock policy, the 16 px template menu-bar glyph, `vibrancy: 'window'` when transparency is not reduced, the `floating` overlay level with `visibleOnFullScreen`, the `x-apple.systempreferences` deep links and the `askForMediaAccess('microphone')` prompt.

Methods take narrow "port" objects (`MediaAccessPorts`, `WindowMaterialPorts`, `OverlayLevelPorts`, `AppearancePorts`, `TrayImagePorts`, `SafeStoragePorts`) instead of Electron classes. Production passes `systemPreferences`, the `BrowserWindow`, `nativeImage` and `safeStorage` directly; `tests/platform.test.ts` passes recording fakes and asserts the exact calls for all three platforms without starting Electron.

What the Windows object decides:

| Area | `win32.ts` decision |
| --- | --- |
| Presence | `appPresence: 'taskbar'`, `recoveryMenuName: 'Tray'`, `supportsHiddenAppIcon: false`, `quitsWhenAllWindowsClosed: true` |
| Permissions | `screenPermissionRequired: false`, `screenAccessGatesSystemAudio: false`, `promptsForMicrophone: false`; `permissionStatus('screen')` is `not-required`; `permissionSettingsUrl` is `ms-settings:privacy-microphone` for the microphone, `ms-settings:sound` for computer audio and `null` for the screen; `systemAudioUnavailableMessage` names the default playback device in Windows Sound settings |
| Microphone | `microphoneAccess` reads `getMediaAccessStatus('microphone')` and blocks `denied` (the per-user switch) and `restricted` (the device-wide switch or group policy) |
| Window options | overlay: `thickFrame: false, minimizable: false` (`index.ts` sets `skipTaskbar` and `maximizable: false` for the overlay on every platform); workspace: `autoHideMenuBar: true`; `supportsWindowMaterial: false`, so `windowBackground` is solid `#111111`/`#f5f5f7` except the transparent overlay |
| Overlay level | `setAlwaysOnTop(true, 'screen-saver')`; `setVisibleOnAllWorkspaces` is not called |
| Appearance | subscribes to `systemPreferences` `color-changed` (`WM_SYSCOLORCHANGE`, which contrast-theme switches broadcast) in addition to `nativeTheme` `updated` |
| Tray | the packaged `resources/icon.png`, resized to 32 × 32, not a template image; the file is listed in electron-builder `files` because electron-vite's `?asset` import of the public directory resolves to that path instead of copying it under `out/` |
| Credentials | `credentialStoreName: 'Windows credential protection (DPAPI)'`; availability is `safeStorage.isEncryptionAvailable()` alone, because `getSelectedStorageBackend()` is Linux-only |
| Identity | `appUserModelId: 'com.faangin.desktop'`, `defaultDeviceName: 'Windows PC'` |
| Launch at login | `applyLoginItem` rewrites the `Run` value on every settings save and once at startup for a user who opted in, carrying the existing `enabled` state through so a Task Manager disable survives; macOS and Linux write only on save |
| Menus and text | `menuLabel` doubles `&` in native menu labels; `legacyTextEncoding: 'windows-1252'` lets a `.txt` or `.md` profile import fall back to the ANSI code page after UTF-8 |
| Shortcuts | `globalShortcutRepeatGuardMs: 1100` swallows keyboard auto-repeat of a held global chord (see Shortcuts) |

To add a capability: declare it in `types.ts` first, implement it for all three platforms (a no-op is a valid answer), keep `types.ts` free of runtime Electron imports (type-only imports are erased), put any user-facing copy that names the OS or its settings app on the platform object rather than in the caller, and add the three expectations to `tests/platform.test.ts`. The contract file header records the same rules. During the current port phase the contract is frozen; a caller that needs something the contract lacks implements a local, commented stopgap and reports it as a contract gap. The one such stopgap in the tree is the `platform === 'win32'` fallback in `displayMediaResponse` (`src/main/capture-permissions.ts`), described under Permissions model.

## Permissions model

Windows has no screen-recording permission. `systemPreferences.getMediaAccessStatus('screen')` always returns `granted` there, so `win32.ts` reports `not-required` without consulting the OS, `screenPermissionRequired: false` skips the startup "screen recording denied" check, and `permissionSettingsUrl('screen')` is `null`, so `openPermissionSettings('screen')` fails with "Your system has no settings page for this permission." and the renderer's `platformCopy('win32').canOpenSettings('screen')` hides the button. Computer audio has no permission either: `permissionSettingsUrl('system-audio')` deep-links to `ms-settings:sound`, the Sound page where the captured default playback device is chosen, a failed check carries `systemAudioUnavailableMessage` ("Computer audio could not be verified. Make sure a playback device is set as default in Windows Sound settings, then retry the access check."), and the setup screen's computer-audio help names **Settings → System → Sound** with an **Open Windows Settings** button beside **Retry audio check**. For the microphone the setup screen's button reads "Open Windows Settings" and its help text reads "Open Settings → Privacy & security (Privacy on Windows 10) → Microphone and turn on microphone access for this device and for desktop apps" (`src/shared/platform-copy.ts`; the toggle names differ between Windows 10 and 11, so the action describes what each switch does), with no restart note. A failed computer-audio check on Windows is `unavailable`, never `denied`, so the setup screen shows the Sound help with **Open Windows Settings** and **Retry audio check** for `unavailable` as well.

The microphone is governed by the global privacy switch in **Windows Settings → Privacy & security → Microphone** (Privacy → Microphone on Windows 10), with the switches for the device and for desktop apps. Electron reads it through `getMediaAccessStatus('microphone')` without prompting; there is no per-app prompt to await, so `promptsForMicrophone: false` and setup never waits for an OS dialog. Immediately before capture starts, `microphoneAccess` reads the switch: `denied` (Electron's mapping of the per-user switch) and `restricted` (the device-wide switch or group policy) stop capture with "Microphone access was denied: Windows has it turned off for apps. Turn it on in Windows Settings → Privacy & security (Privacy on Windows 10) → Microphone, then try again." (the word "denied" is deliberate: the renderer's meter, guidance and question-source classifiers key on it, as they do for the macOS message); the message names the page in text only, and the `ms-settings:privacy-microphone` deep link is reached through the **Open Windows Settings** button on the microphone row in Settings → permissions and in the setup screen (`openPermissionSettings('microphone')`). `not-determined` and `unknown` are allowed because Chromium still opens the device in those states. If the switch is turned off while a session is running, the capture renderer's device request fails inside Chromium rather than through this check; that path has not been exercised on Windows.

Computer audio is Chromium's WASAPI loopback. The display-media request handler in `index.ts` answers through `displayMediaResponse` (`src/main/capture-permissions.ts`) with the primary screen source and `audio: 'loopback'`, which Electron documents as capturing system audio and as supported only on Windows (macOS reaches the same `respond` call and Electron 44 serves it through its CoreAudio tap instead). On Windows the answer falls back to any enumerated screen when none carries the primary display id, because loopback is device-wide and duplicated or remote displays report an empty `display_id`; that `platform === 'win32'` branch is the one contract-gap stopgap in the tree, pending a `DesktopPlatform` decision on whether loopback is tied to a display, while macOS keeps the strict primary match. No OS consent dialog appears and no screen-recording status is consulted, so `screenAccessGatesSystemAudio: false` lets the setup audio check run without a screen permission. Faangin uses `loopback`, not `loopbackWithMute`, so the call keeps playing locally while it is transcribed. The in-app one-time computer-audio notice and its acknowledgement still gate the first system-audio session on every platform; the OS not asking does not remove the application's consent step.

A loopback is bound to one render endpoint, so unplugging a headset, a Bluetooth profile switch or removing a USB DAC ends the stream while nothing was revoked. Where screen consent gates computer audio (macOS) a stopped source clears the verified-access receipt and sends the user back to setup; on Windows `sourceLossEffects` (`src/main/capture-loss.ts`) keeps the receipt, and `Audio device disconnected.` from either source reconnects the surviving source through `scheduleDeviceReconnect`, which reacquires both on the new default device. A silent stall (`No audio frames`) leaves the microphone running and shows the error. The Windows silent and low-level loopback hints (Default Device versus Default Communications Device) are shown in full in the audio guidance, because the meter clips them to one line, and the Windows "No computer audio was provided" status reads as an unavailable source.

Screenshots pair a screen source with its display through `display_id`. Windows leaves it empty for a duplicated (Win+P Duplicate) or remote display, so `resolveScreenshotSource` pairs one unlabeled screen source with the display only when exactly one display exists and it is the same display before and after the capture; with several displays an unlabeled screen is still refused rather than guessed. macOS always supplies the id, so that branch is unreachable there.

What is verified: `tests/platform.test.ts` asserts the `not-required`/`null` screen answers, the `ms-settings:sound` link, the microphone `denied` and `restricted` message, the pass-through of Electron's microphone statuses, and that `unknown` never blocks; `tests/capture-permissions.test.ts` covers the any-screen fallback. What is not: whether the deep links open their Settings pages, which of `denied` and `restricted` each switch reads as on a real machine, and whether loopback yields audio frames from a conferencing application.

## Overlay

The overlay is a frameless, transparent, always-on-top `BrowserWindow` on every platform. On Windows `overlayWindowOptions` adds `thickFrame: false` (Electron drops the thick frame for transparent windows anyway; declaring it keeps the trade-off visible: no DWM shadow or window animation and no edge-drag resizing, so the renderer's `overlay-resize` IPC and the visible resize grip remain the resize path). `index.ts` gives the overlay `skipTaskbar: true` (removes the taskbar button; Alt+Tab still lists the window) and `maximizable: false` on every platform, because double-clicking an app-region drag area toggles maximize on Windows, which would push the overlay past its layout limits, and it unmaximizes and re-applies the layout if that happens anyway; `OverlayInteractionPolicy` re-asserts `setSkipTaskbar(true)` after every `setFocusable` call, which Windows couples to the taskbar button, and applies `setIgnoreMouseEvents` and `setFocusable` only when the window or the click-through mode changed: on Windows `setFocusable` also deactivates the window (macOS keeps focus), so repeating it on every answer, nudge or toggle would take keyboard focus from the composer and hand the foreground away. The overlay is `minimizable: false` on Windows because a minimized overlay has no taskbar button to restore it from, and `index.ts` cancels `system-context-menu` for it so right-clicking the drag region does not raise the native window menu.

`applyOverlayLevel` calls `setAlwaysOnTop(true, 'screen-saver')`. Windows has a single topmost tier (`HWND_TOPMOST`); every Electron level above `normal` maps to it, so the overlay is interleaved by activation order with every other topmost window, including conferencing share toolbars and anything else that sets topmost. There is no guarantee over exclusive full-screen (DirectX exclusive) applications or the secure desktop. `setVisibleOnAllWorkspaces` is `darwin,linux` in Electron, so it is not called; a window belongs to one virtual desktop and Faangin does not pin itself across desktops. Click-through is the existing explicit opt-in (`setIgnoreMouseEvents`), unchanged.

Content protection (**Settings → Visibility & data → Exclude from screen capture**, off by default) calls `setContentProtection`, which Electron supports on `darwin,win32`. On Windows it maps to `SetWindowDisplayAffinity` with `WDA_EXCLUDEFROMCAPTURE` on Windows 10 2004 and later (the window is omitted from Windows.Graphics.Capture and DXGI desktop duplication captures); older builds fall back to `WDA_MONITOR`, where capture shows a black rectangle. The change takes effect with the next desktop composition, so a capture started immediately after toggling can still contain the window. Protection also applies inside a Windows remote session: the Remote Desktop client still shows the window to the remote user, but remote-access software that captures the desktop cannot see it, unless the `AllowWindowCaptureExclusionInRemoteSessions` Chromium feature is disabled at startup (Faangin does not disable it), in which case `isContentProtected()` still reports `true`. Capture paths that bypass the compositor (hardware capture devices, cameras pointed at the screen) are unaffected by any affinity. The setting remains a requested capture policy, not a visibility guarantee, as `architecture.md` already states.

Verified: `tests/native-policy.test.ts` models Windows deactivating a window on `setFocusable` and asserts reveals never repeat it; `tests/platform.test.ts` asserts the exact overlay options, the `screen-saver` level and that no workspace call is made. Not verified: z-order over Teams, Zoom or Meet, behaviour over full-screen games or presentations, multi-monitor and mixed-DPI placement, and what a given sharing application captures with exclusion on or off.

## App presence

Faangin is a taskbar application on Windows. `supportsHiddenAppIcon: false` keeps the **Hide Dock icon** Settings toggle and the **Show in Dock** menu item macOS-only; `MacDockPolicy` is a no-op elsewhere. The tray icon is `resources/icon.png`, imported in `index.ts` through electron-vite's `?asset` import and resized by the platform object to 32 × 32 (crisp in the notification area at 200% scaling and clean when downsampled; Windows has no template-image tinting). electron-vite treats `resources/` as the main-process public directory and resolves the import to `out/main/../../resources/icon.png` instead of copying the file, so electron-builder `files` lists `resources/icon.png` explicitly and the asar carries it at that path; `tests/release-config.test.ts` pins the entry. Left-clicking the tray icon shows the workspace, because a taskbar OS opens the tray menu on right-click only; the right-click menu is the same recovery menu as the macOS menu-bar extra: version, Show workspace, Show overlay, Reset overlay size & position (rendered with `menuLabel`, which escapes `&` as `&&` because Windows menus treat a single `&` as a mnemonic marker and would draw "Capture  solve"), Make overlay interactive, Click-through overlay, the action list, Settings and Quit. Overlay recovery copy says "Tray" where macOS says "Menu bar".

Framed workspace windows are created with `autoHideMenuBar: true`, so the application menu that `Menu.setApplicationMenu` installs does not paint a menu bar on Windows; pressing Alt reveals it. The tray menu is the always-available recovery path. At startup `app.setAppUserModelId('com.faangin.desktop')` is called; the value equals the electron-builder `appId`, so taskbar grouping and pinning attribute windows to the installed shortcut (`tests/platform.test.ts` and `tests/release-config.test.ts` pin both sides).

`quitsWhenAllWindowsClosed: true` follows the Windows convention, but closing a Faangin window hides it rather than closing it, so `window-all-closed` rarely fires outside the smoke harness. Windows ends a session (log-off, restart, shutdown) without `before-quit` and allows no asynchronous work afterwards, so each UI window handles `session-end` by flushing storage, ending the live capture session (`endSessionAtShutdown`: status `ended` with the real time, and the transcript flagged incomplete when speech was still being transcribed, instead of the next launch stamping its own time) and disposing the dock policy, appearance subscription, capture policy, window state, requests, licensing, shortcuts, tray and repository synchronously.

## Shortcuts

Accelerators are normalized per platform in `src/main/shortcut-manager.ts`. On win32 `CommandOrControl` becomes `Control`, `Command` is rejected ("Windows has no Command key. Use Ctrl, Alt or Shift instead."), labels render `Ctrl`, `Alt` and `Win`, and the Faangin preset's **Stop** default moves from `CommandOrControl+Shift+Escape` to `Control+Alt+Escape`, because Ctrl+Shift+Esc opens Task Manager and can never be registered. The Cue preset receives the same stop replacement.

| Action | Windows default |
| --- | --- |
| Capture & solve | Ctrl+Alt+S |
| Toggle overlay interaction | Ctrl+Alt+I |
| Show workspace | Ctrl+Alt+W |
| Assist | Ctrl+Enter |
| Solve | Ctrl+Shift+Enter |
| Capture screenshot | Ctrl+Shift+S |
| Show / hide overlay | Ctrl+Shift+Space |
| Stop capture | Ctrl+Alt+Escape |

`normalizeAccelerator` rejects chords Windows consumes before any `RegisterHotKey` sees them, with a reason shown in Settings: Ctrl+Shift+Escape (Task Manager), Ctrl+Alt+Delete (secure sign-in), Ctrl+Escape (Start menu), Alt+Tab, Alt+Shift+Tab and Ctrl+Alt+Tab (window switching), Alt+Escape and Alt+Shift+Escape (window cycling), Alt+F4 (registering it would hijack window close everywhere) and any combination with the Windows key (`Super`). The thrown reason is what `previewShortcuts` in `Settings.tsx` shows below the shortcut table before anything is saved and what the save path returns as its error message; a saved reserved override fails cleanly while the registered shortcuts stay unchanged. The same inputs still normalize on macOS and Linux.

Held chords: Chromium registers global hot keys with `RegisterHotKey` and no `MOD_NOREPEAT`, so Windows posts a callback for every keyboard auto-repeat of a held chord. `ShortcutManager` swallows callbacks for one chord that arrive within `globalShortcutRepeatGuardMs` (1100 ms on Windows, 0 elsewhere) of the previous callback for that chord, dropped ones included, so a hold of any length is one press and a new press needs 1.1 s of silence on that chord. Consequently a deliberate second press of the same chord inside that window is ignored. Overlay nudges and answer scrolling are exempt so holding them keeps moving. This follows from Chromium's source rather than a measurement on hardware.

AltGr caveat: on keyboard layouts where the right Alt key is AltGr (most non-US layouts), Windows reports AltGr as Ctrl+Alt. A registered Ctrl+Alt+<letter> hotkey can therefore fire when the user types an AltGr character, and can shadow that character in other applications. Faangin's Ctrl+Alt defaults (S, I, W, Escape) are subject to this; a user on such a layout can override them in Settings. Which layouts and letters collide in practice is a physical-acceptance item.

Verified: `tests/shortcut-manager.test.ts` covers the win32 stop default, every reserved chord and its message, the Windows-key rule, the Command rejection, labels, that no default is reserved, startup application on win32 and the retired-preset override migration; `tests/settings-shortcut.test.ts` covers the Ctrl-only local Settings shortcut. Not verified: whether another installed application already owns a default, and AltGr behaviour on real layouts.

## Credentials and storage

Provider keys are encrypted with Electron `safeStorage`, which uses DPAPI on Windows. `credentialEncryptionAvailable` is `isEncryptionAvailable()` alone (the Linux backend check does not apply), and unavailable storage surfaces as "Windows credential protection (DPAPI) is unavailable. Sign in to your Windows account and restart Faangin." on read, or "…, so no key was saved. Sign in to your Windows account and try again." on save. The threat model is the one in [architecture.md](architecture.md#persistence-and-secrets): DPAPI protects the ciphertext against other Windows users, not against every process running as the same user, and nothing encrypts the transcript database.

Profile import decodes `.txt` and `.md` files through `decodeProfileText` (`src/main/profile-text.ts`): UTF-8 first, a UTF-16 byte order mark (Notepad "Unicode", PowerShell 5.1 redirection) through its own decoder, and the Windows ANSI code page (`legacyTextEncoding`) only after UTF-8 fails; macOS and Linux keep refusing non-UTF-8 text. `window-state.json` is replaced through a temporary file and `renameSync`, retried up to five times (at most 250 ms) on `EPERM`, `EBUSY` and `EACCES`, which antivirus and the search indexer cause on NTFS and POSIX never reports.

`app.getPath('userData')` is `%APPDATA%\Faangin` (from `app.setName('Faangin')` in `index.ts`, which Electron applies to the userData path; `package.json` has no `productName`, so without that call Electron would use `faangin`), holding `faangin.sqlite`, the offline licence and account store, saved settings and the `persist:faangin-ui` session partition. The `mkdirSync(..., { mode: 0o700 })`, `chmodSync(..., 0o700)` and `mode: 0o600` calls that harden these files on POSIX are no-ops on NTFS; protection comes from the per-user ACL that `%APPDATA%` carries and that new files inherit. Tests that assert owner-only POSIX bits are platform-conditional (`tests/licensing-store.test.ts` checks only that the file is writable on win32). The NSIS installer places the program under `%LOCALAPPDATA%\Programs\Faangin` for the current user (`perMachine: false`, `requestedExecutionLevel: asInvoker`, no elevation) and `deleteAppDataOnUninstall: false` keeps `%APPDATA%\Faangin`, so reinstalling preserves the licence, account store and encrypted keys.

## Build, package, release

Prerequisites on Windows are Windows 10 2004 or later or Windows 11 on x64, Node.js 22.13 or newer and the same commands as macOS from PowerShell or cmd: `npm ci`, `node node_modules/electron/install.js`, `npm run dev`. No native toolchain is needed; storage uses `node:sqlite` and `npmRebuild` is off. electron-builder downloads NSIS itself. Developer Mode is not required to run or package; tests that create symlinks skip that assertion when Windows refuses without it.

| Command | Produces |
| --- | --- |
| `npm run package:win` | `npm run build` then `electron-builder --win --x64 --dir`: `dist/win-unpacked/Faangin.exe` |
| `npm run dist:win` | `npm run build` then `electron-builder --win --x64`: `dist/win-unpacked/` plus the NSIS installer `dist/Faangin-0.4.3-Windows-x64-setup.exe` (unsigned; SmartScreen warns) |
| `npm run release:win` | `scripts/release-win.mjs`: signed installer, verification and `SHA256SUMS` in `dist/release-win` |
| `npm run icons` | `scripts/icons.mjs`: regenerates `resources/icon.png`, `resources/icon.ico` and, on macOS, `resources/icon.icns` |

The installer configuration in `electron-builder.yml` is `win.icon: resources/icon.ico`, `target: nsis`, `arch: [x64]`, `artifactName: Faangin-${version}-Windows-${arch}-setup.${ext}`, `requestedExecutionLevel: asInvoker`, `signtoolOptions.publisherName: Muhammed Salim` (the publisher electron-builder records for signature verification, defaulting to the certificate's common name; without `CSC_LINK` it skips signing, and the installer's CompanyName comes from `package.json` `author`), and `nsis`: `oneClick: false`, `perMachine: false`, `allowToChangeInstallationDirectory: true`, `createDesktopShortcut: true`, `shortcutName: Faangin`, `deleteAppDataOnUninstall: false`, `runAfterFinish: true`. `tests/release-config.test.ts` pins every value and the `package:win`, `dist:win`, `release:win` and `test:win32` scripts. `resources/installer.nsh` (picked up from `buildResources`) adds a `customUnInstall` macro that deletes the `Run` and `StartupApproved\Run` values named after the appId, skipped on update, because electron-builder's uninstaller never removes the login item Electron registers and an uninstall with **Launch at login** on would otherwise leave a startup entry for a missing executable. The startup reconcile in `index.ts` repairs a `Run` value that points at a previous install directory.

`resources/icon.ico` is committed so no build host needs an icon conversion toolset. `scripts/icons.mjs` renders `resources/icon.svg` with sharp at 16, 24, 32, 48, 64, 128 and 256 px and `scripts/lib/ico.mjs` writes them as PNG-compressed ICO entries without any image library (Windows Vista and later read PNG entries directly; 256 is the largest size the format can describe). `tests/ico.test.ts` checks the directory layout, the 256 px zero-width encoding and the committed file.

`npm run release:win` mirrors `release:mac`. It refuses to run anywhere but win32 ("Windows releases require a Windows host with the Windows SDK signing tools (signtool)."), requires exactly one signing strategy, either `CSC_LINK` and `CSC_KEY_PASSWORD` for a `.pfx` certificate or Azure Trusted Signing through `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_CODE_SIGNING_ENDPOINT` (HTTPS), `AZURE_CODE_SIGNING_ACCOUNT_NAME` and `AZURE_CERTIFICATE_PROFILE_NAME`, and locates `signtool.exe` on `PATH` or in the newest installed Windows 10/11 SDK. `--check` stops there. A real run builds, clears `dist/release-win` (the unsigned `dist/win-unpacked` is preserved), packages with `electron-builder.release-win.yml` (`forceCodeSigning: true`, `verifyUpdateCodeSignature: false` and `differentialPackage: false` because there is no updater) and `--publish never`, adds `win.azureSignOptions` per run for the Azure strategy so the config file never names an account (its required `publisherName` is read from the release config's `signtoolOptions`, so the certificate subject is declared once), runs `signtool verify /pa /v` on `win-unpacked/Faangin.exe` and the installer and requires both "Successfully verified" and a secure timestamp, removes `.blockmap` and channel manifests, and writes `SHA256SUMS` over the installer. It never publishes. Only environment variable names appear in its diagnostics. `tests/release-win.test.ts` covers the host guard, the strategy rules, secret non-disclosure, signature verification, checksums, metadata removal and the `--check` CLI. No signed Windows artifact has been produced.

`.github/workflows/desktop-ci.yml` runs the build, tests and development smoke on `macos-15` and `windows-latest` with Node 22. Both jobs build unpacked apps with `FAANGIN_PACKAGE_QA=1`, run the packaged smoke with disposable profiles and label the uploaded builds `qa-only`. The Windows job runs native QA for first run, required access and overlay geometry. It rebuilds with QA disabled for the separate `faangin-windows-installer-unsigned` artifact. Public distributions use the signed release scripts, which disable packaged QA. The November 3 baseline passed both native CI jobs, including the Windows packaged smoke, native QA suites and unsigned installer build. | `npm run test:win32` | Developer Mac, CI `macos-15` | `node --import tsx --import ./scripts/simulate-platform.mjs --test tests/*.test.ts`; the preload defines `process.platform` as `win32` for the test process so code that defaults to the running platform takes its Windows branch, pins `TEMP`/`TMP` to the real temp directory (Node's `os.tmpdir()` switches to those variables once it sees win32) and sets `FAANGIN_SIMULATED_PLATFORM=win32`. Node's `path` keeps the host's separators, so the one test that loads electron-builder's schema validator (`tests/release-config.test.ts`, through app-builder-lib's jiti loader, which rewrites `__filename` to backslashes under win32) skips itself with that reason when the variable is set; the native `npm test` and the `windows-latest` job run it. `package.json` defines the script and `tests/release-config.test.ts` pins its text |
| `npm test`, `npm run build`, `npm run smoke` on `windows-latest` | CI | Compiles and loads the main, preload and renderer bundles under Windows, runs the Windows branches with the real `process.platform`, and drives the isolated sandboxed desktop workflow (preload/IPC, SQLite, document import, localhost provider fixture) in a development build and again against `dist/win-unpacked/Faangin.exe`. `scripts/smoke.mjs` accepts the `.exe` or the `win-unpacked` directory and on win32 stops the app with `taskkill /PID` (WM_CLOSE, so `app.quit` runs and SQLite flushes), falling back to `process.kill` and then a hard kill after the grace period |
| `npm run package:win` and the installer step on `windows-latest` | CI | electron-builder completes the unpacked app and an unsigned NSIS installer on a Windows host; both are uploaded as workflow artifacts |

The smoke runs with the access fixture (`FAANGIN_SMOKE_ACCESS_FIXTURE=ready`), so it does not exercise `getMediaAccessStatus`, the microphone switch or loopback capture; it proves the application starts and operates on Windows, not that audio flows. The explicit native audio check described in [audio-permissions.md](audio-permissions.md#verification) accepts the Windows executable, since `resolveAppExecutable` (`scripts/lib/app-executable.mjs`) treats a `.app` bundle or an unpacked output directory as a container and any other path as the executable; from PowerShell: `$env:FAANGIN_APP_PATH="$PWD\dist\win-unpacked\Faangin.exe"; $env:FAANGIN_SMOKE_NATIVE_AUDIO=1; npm run smoke`. It has not been run on Windows.

What remains for a physical Windows machine, in acceptance order:

1. Install `Faangin-0.4.3-Windows-x64-setup.exe` on a clean Windows 10 2004+ or Windows 11 x64 user profile; confirm the per-user install location, desktop shortcut, taskbar grouping under one button, Start menu entry, uninstall leaving `%APPDATA%\Faangin`, and SmartScreen behaviour for the unsigned build.
2. Microphone: with the privacy switch on, off, and turned off mid-session (on Windows 10 and 11, to check both wordings of the path); confirm the message for the state each switch reports (`denied` or `restricted`), that `ms-settings:privacy-microphone` opens, and recovery after re-enabling.
3. Computer audio: loopback from Teams, Zoom and Meet through speakers and through a headset; verify words in **Conversation**, not only meters; confirm the one-time notice gates the first session and that no OS dialog appears; unplug the headset and switch a Bluetooth headset between its A2DP and HFP profiles mid-session and confirm the session restarts on the new device instead of returning to setup; capture a screenshot under Win+P Duplicate and in Remote Desktop.
4. Overlay: topmost over each conferencing application and its share toolbar, over full-screen presentations and games, across virtual desktops, on multiple monitors with mixed DPI; drag, grip resize, collapse/expand, click-through toggle and recovery from the tray menu.
5. Content protection on and off in each sharing application's window and screen share modes, including a remote session.
6. Shortcuts: every default registers on a fresh machine; hold Ctrl+Shift+Space and Ctrl+Alt+S past the repeat delay and confirm one action; hold an overlay nudge and confirm it keeps moving; conflicts with installed software; AltGr behaviour on a non-US layout; the reserved-chord messages in Settings.
7. Appearance: Transparency effects off, Animation effects off, contrast themes, Narrator; confirm the `color-changed` refresh and solid surfaces, and that toggles, the audio meter, status dots and selected tabs stay distinguishable under every contrast theme (`forced-colors.css`).
8. Lifecycle: log-off and restart with a session open (`session-end`; confirm the session shows the real end time), Launch at login (disable it in Task Manager, change an unrelated setting and confirm it stays disabled; uninstall with it on and confirm no `Run` entry remains), single-instance focus, quit from the tray. Overlay focus: type in the composer while an answer lands and confirm focus stays, with no taskbar flicker; right-click the logo and confirm no system menu.
9. Credentials: DPAPI save, read after restart, and the unavailable-store message under a profile where DPAPI fails.
10. Signed release: `npm run release:win -- --check`, a real signed run, `signtool verify` output, `SHA256SUMS`, and SmartScreen reputation for the signed installer over time.

Until these run, Windows is a built and unit-tested target, not an accepted one. See [release readiness](release-readiness.md#signed-windows-release) for the signing setup, [build status](build-status.md#windows-port-043) for the recorded checks, and [feature status](feature-status.md#windows-port-043) for the requirement ledger.
