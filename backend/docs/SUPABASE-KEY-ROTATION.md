Supabase's current incident guide requires replacing and deleting the exposed modern secret. For an exposed legacy service-role JWT, it requires **both deactivating the legacy API keys and revoking the legacy JWT signing secret**. Disabling legacy API-key use alone can leave the JWT accepted by services that trust its signer. The legacy anon/service-role pair cannot be independently reissued. [Official leaked-key rotation guide](https://supabase.com/docs/guides/security/rotate-leaked-api-keys), [legacy-key rotation guidance](https://supabase.com/kb/troubleshooting/rotating-anon-service-and-jwt-secrets-1Jq6yd).

Hosted Edge provides the secret-key map by key name and reserves `SUPABASE_*` from custom secret writes. A singular custom `SUPABASE_SECRET_KEY` is not a viable hosted override. Documentation does not guarantee that deleting `default` retargets it to a different named key or refreshes an already-created client on a specified schedule. All four functions intentionally use `verify_jwt=false` and enforce their own Auth/signature checks; that remains appropriate.
